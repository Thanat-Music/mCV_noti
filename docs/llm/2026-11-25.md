## 2. User decisions and implemented changes

### Homework reads cached data

The initial implementation requested a fresh assignment fetch for each `homework`. The user explicitly rejected that behaviour: push-triggered and daily updates are sufficient.

Current local implementation:

- `Engine.queue_homework()` only queues a command response. It does not increment `push_refresh.requested`.
- `Engine.prepare()` does not wait for an unrelated pending refresh.
- The response includes the last successful update time, followed by the original assignment Flex cards.
- If no successful snapshot exists, it says data is not available yet instead of claiming there are no assignments.
- The interval is `[00:00 today, 00:00 today + 8 days)` in Bangkok time: today plus seven following calendar days.
- All active assignment statuses in that interval are included, including submissions and earlier deadlines from today. Items with no due date are excluded.
- Startup, incoming-push, daily 06:00 Bangkok and failure-retry reconciliation rules are unchanged.

Files: `engine.py`, `tests/test_notification_features.py`, `docs/notifications.md`.

### Push classification and independent preferences

The user wanted announcements, materials and other incoming mCV notifications, with separate settings for each category.

The Pi stores decrypted payload JSON in `push_inbox.payload`. Payload content is not emitted to journal logs. Processed rows are removed after seven days; pending rows are retained. The user supplied real stored samples, so classification can be grounded in those examples.

Observed payload shape: `icon`, `message`, `silent`, `title`, `url`.

| Signal | Interpretation | Evidence |
| --- | --- | --- |
| Final ` - Assignment` | Assignment | Genuine HW6/HW7 and exam-submission payloads |
| Final ` - Material` | Learning material | Genuine exam code-template payload |
| Final ` - Score` | Score | Genuine Lab 9 payload; URL links only to the course |
| Final ` - Announcement` | Announcement | User-authorized guess; not observed, visibly marked unverified |
| URL query route `courseville/course/<course>/assignment/<id>` | Assignment fallback | Genuine samples |
| URL query route `courseville/course/<course>/material/<id>` | Material fallback | Genuine sample |

`message` is the course title in these samples. `icon` often contains `files/`; it must never cause material classification. The samples do not distinguish a new assignment from an edit; detecting an actual assignment change remains the snapshot engine's responsibility.

Classifier order in `push_types.py`:

1. Match a recognized final standardized suffix in the title, including nested notification/data containers. Earlier words in the title are not classification signals.
2. If there is no recognized suffix, inspect explicit type/category/event metadata and known CourseVille URL route segments.
3. Ambiguous/conflicting signals or unknown formats fall into Other.

Settings now expose assignment, announcement, material, score and other push categories. Old saved `courseville_push` preferences become defaults for these categories, preserving an opt-out. Existing pending legacy unclassified messages follow Other. Push dedupe keys remain unchanged. Filtering LINE notifications does not prevent refreshing assignment data.

### Readable LINE status and help

Previously `status` was one sentence claiming the service was running plus a last-refresh timestamp.

`status.py` now formats blocks for assignments, incoming pushes and LINE deliveries. It reports saved refresh outcome/last success, assignment count in the homework interval, last retained push time, pending inbox count and pending/failed outbox counts. It explicitly says this is stored state, not a live connection probe. Outbox counts are measured before queueing the status reply itself.

Default help now separates `homework`, `status` and `settings` with blank lines. The user requested the footer `Contact dev for account setup.` Keep that wording unless the user changes it.

## 3. SSH dashboard and multi-user administration

The user requested a dashboard opened on a notebook through SSH, plus adding/removing users. Clarification confirmed that each user has their own CourseVille account and LINE identity, rather than several recipients sharing one CourseVille account.

### Runtime structure

- The default CLI still supports the original single-account worker.
- `--multi-user` runs `supervisor.py`; the Pi unit now enables it with `--admin-port 8081`.
- The supervisor manages one isolated existing worker per approved/enabled account, reusing the original daemon with an injected stop event and ready callback.
- `u1` retains the original runtime database and receiver identity.
- Other accounts use `users/<internal-id>.db` next to the primary runtime database.
- Registry/encrypted credentials stay in the legacy database's `user` table; additional admin tables contain metadata, invitations, signup delivery state and audit events.
- Existing non-primary legacy accounts are imported paused, not silently activated.
- Account edits increment a revision; the supervisor stops/restarts the affected worker. A lock serializes lifecycle changes and reconciliation.
- Unexpected worker termination is backed off 30 seconds, even though daemon cleanup sets its stop event. This case has a regression check.

### Listeners and routing

| Listener | Routes | Access |
| --- | --- | --- |
| `127.0.0.1:8080` | `/callback`, `/healthz`, `/register`, `/settings/<user-id>` | Existing public LINE tunnel |
| `127.0.0.1:8081` | Dashboard and `/api/...` admin endpoints | SSH port forwarding only |

The shared callback verifies LINE's signature, then routes commands by authenticated `source.userId`. Each account's event dedupe and command outbox remain in its own state database. Settings tokens are scoped to the account-specific settings path, so a token from one account cannot configure another.

The dashboard uses a separate loopback listener, loopback Host checks, cross-site request checks and a per-process anti-CSRF header for mutations. SSH provides the admin authentication boundary; there is no separate web admin login. Local processes on the Pi are trusted. Do not expose port 8081 through a public tunnel.

### Dashboard features

- User/approval/running-worker/failed-delivery overview and live-send versus dry-run mode.
- Manual add, edit display name/password/LINE binding, approve, pause/resume and delete.
- Per-user saved assignments, recent push previews, delivery state/attempt counts and notification preferences.
- Explicit manual CourseVille update action, which obeys existing backoff.
- Read-only view refresh every 15 seconds while visible; it never automatically requests CourseVille updates.
- Recent admin audit records without credentials.
- Assignment table is capped at 300 items; recent push/delivery tables show up to 30 rows.
- Rendering uses DOM text content, not remote strings inserted as HTML. No credential values, receiver private keys or signup/settings URLs are returned in snapshot APIs.
- Unsaved preference edits are not overwritten by automatic view updates.

Passwords use the existing RSA-OAEP scheme, compatible with `legacy_account()`. They are not returned by admin APIs. Changing a CourseVille username for an existing user is rejected: create a new user for another identity so old cached assignments cannot carry over. Password changes with the existing username are allowed.

Deleting an account stops its worker, removes credential/recipient rows, marks the admin record deleted and invalidates outstanding signup invitations. Runtime/history databases remain on disk. This is not a data-erasure operation. Pausing also retains history and pending work; resuming follows existing expiry and eligibility checks.

## 4. Registration without manual LINE UID entry

The user correctly noted that normal users do not know their LINE UID. The chosen flow avoids manual key search and pairing:

1. A user adds the bot and sends `start`.
2. The signed event supplies the LINE UID. `enrollment.py` creates a sender-bound signup token and queues a private reply to the same recipient.
3. The one-time link expires after 15 minutes. New links invalidate older unused links. Duplicate webhook events reuse the same token and do not duplicate reply queue rows. Limit: three fresh links per minute per LINE identity.
4. The user opens `/register`, enters display name and CourseVille credentials. The browser never supplies the LINE UID used for binding.
5. A pending, disabled account is created. Admin selects Approve before its worker can start.

Signup replies have a durable outbox with stable LINE retry keys. They use push delivery and require `--send`, so channel quota still applies. Pending signup replies expire after 15 minutes; completed signup outbox records are retained for seven days. A separate delivery loop avoids waiting for LINE API calls inside the webhook callback.

Credentials are encrypted at rest, not hidden from the operator who controls the private key. Registration does not itself prove the supplied CourseVille password is valid; check the first worker refresh after approval.
